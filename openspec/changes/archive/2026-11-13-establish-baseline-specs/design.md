# Design

## Context

Код не меняется: change только фиксирует спецификации. Поэтому design описывает не реализацию, а правила, по которым составлены спецификации. От этих правил зависят последующие changes-исправления. Мотивация — в proposal.md (Why).

## Goals / Non-Goals

**Goals:**
- Зафиксировать границы capability так, чтобы будущие исправления ложились в одну capability и не пересекались.
- Сделать так, чтобы каждое исправление дефекта приносило собственное проверяемое требование.

**Non-Goals:**
- Описывать дефекты как требования. Даже в виде «как есть».
- Описывать реализацию: классы, хранилища, библиотеки.
- Приводить код в соответствие спецификациям: baseline описывает то, что код уже делает.

## Decisions

### Baseline молчит о дефектах
Там, где текущее поведение признано дефектом, спецификация не содержит требования. Требование добавит change-исправление (ADDED/MODIFIED).

- **Альтернатива А**: описать дефект как есть. Отклонено: дефект стал бы контрактом, а исправление выглядело бы как изменение намеренного поведения.
- **Альтернатива Б**: сразу описать правильное поведение. Отклонено: у changes-исправлений не осталось бы дельт, а `openspec validate` отклоняет change без дельт. Кроме того, терялась бы трассируемость «дефект → требование».
- Следствие: формулировки в местах рядом с дефектом намеренно нейтральны. Например, «сезонный список» без года, «выбранный тайтл» без уточнения, к какой карточке он привязан, отсутствие требования к формату счётчика.

### Прогресс серий принадлежит title-catalog
Изменения вышедших серий и статуса «завершён» описаны в title-catalog, хотя их запускает episode-notifications. Каталог — единственный источник правды о состоянии тайтла. episode-notifications лишь ссылается на него.

### bot-runtime — отдельная техническая capability
Сквозное поведение процесса (совместная работа циклов, перезапуск, конфигурация) вынесено отдельно, а не размазано по пользовательским capability. Туда же лягут будущие требования об изоляции ошибок.

### subscriptions не делится
Подписка и управление подписками описаны в одной capability: у них общая семантика (идемпотентность, связь пользователя с тайтлом).

### Явно признанные намеренными
- Каждая озвучка — отдельное уведомление.
- Уведомления не зависят от статуса «завершён». Ранее наблюдавшиеся уведомления по «завершённым» тайтлам объясняются ложным статусом из-за дефекта разбора эпизодов, а не отсутствием фильтра.
- /mysubs показывает завершённые тайтлы.
- Накопившиеся во время простоя входящие отбрасываются.

## Risks / Trade-offs

- [Читатель только спецификации не узнает о существующих дефектах] → Перечень сознательно не описанных областей приведён в proposal.md (What Changes). Каждая из них — будущий change.
- [Нейтральная формулировка может ошибочно читаться как разрешение любого поведения] → Change-исправление для этой области добавляет строгое требование. До тех пор область считается неспецифицированной, а не разрешённой.
- [Утверждения baseline выведены из чтения кода, а не из запуска] → Задачи на сверку каждой спецификации с кодом в tasks.md.
